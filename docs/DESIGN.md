## 一、要解决的问题

DSH 本身很会干活，但**不记得你上次踩过什么坑**。每次开新会话都得重新解释：
"这个项目的回调守卫要放在幂等判断之前"、"别用 float 存金额"。

现有做法有两个极端：

| 做法 | 问题 |
|---|---|
| 云端记忆服务 | 全部开发对话上传到别人的服务器 |
| 本地笔记 / 手写 skill | 只有事实、没有归纳；不会告诉你"这个问题你犯过三次了" |

本项目要的是第三种：**在自己机器上把跨会话的模式找出来，在下次动手前提醒你**，数据不出本机。

### 关键判断：记忆 ≠ 进化

这是整个方案的分水岭。

| | 记忆 | 进化 |
|---|---|---|
| 输入 | **一次**会话的摘要 | **多次**会话 / 多个仓库 |
| 问题 | "以前定过什么？" | "哪里反复出问题？什么做法有效？" |
| 产出 | 一条事实 | 一个可复用的过程，或一条可验证的判断 |
| 关键字段 | 内容 | **复现次数（recurrence）** |
| 失败模式 | 注入噪声挤上下文 | **错误结论被放大成长期约束** |

**"反复出现"才是进化的信号，单次出现只是噪音。**
所以数据模型里 `recurrence` 是一等字段，而不是附带的统计。

### 关键判断：进化单位是 skill，不是结论

参考 Hermes Agent 的做法（`agent/background_review.py` + `agent/curator.py`，实测过其源码）：
它把经验沉淀成 **`SKILL.md` 可复用流程**，而不只是往记忆文件里追加一句结论。
这比"记住一句话"有用得多——因为它是**按需加载的可执行过程**，不占上下文。

所以 Phase 3 的产物是 skill 草稿，而不是更多文本条目。

## 二、五个核心决策

### 决策 1：本地优先，而不是中心服务

**选项**：
- (a) 中心服务 + 客户端（内部版 `dsh-memory` 的形态）
- (b) 纯本地
- (c) 本地优先 + 可选共享

**选 (c)**。

理由：通用版最致命的约束不是技术，是**信任成本**。
一个会读你全部开发会话的插件，如果默认往外发数据，绝大多数人第一反应是卸载。
而"数据全是磁盘上的人可读文件、默认一个字节都不外发"是一个**可以当场验证**的承诺——
用户打开 `~/.dsh-evolution/ledger/` 就能看到。

代价是团队共享变复杂了（没有中心节点）。解法见决策 3。

### 决策 2：账本零 LLM，归纳才花钱

**选项**：
- (a) 每轮结束调 LLM 摘要
- (b) 攒够 N 轮调一次
- (c) 分层：每轮只记结构化账本（零成本），归纳另走一条链

**选 (c)**，并且归纳默认关闭。

理由有两层：

1. **成本**：逐轮调 LLM 是 N 倍开销，而且**看不到"反复出现"**——一次会话内部归纳不出跨会话模式。
2. **可控性**：账本是纯本地的，可以每轮都记、可以回扫几个月历史，成本近似为零。
   这让"先装上看看能记到什么"成为一个**零风险的第一步**。

这也解释了为什么 Phase 0 完全没接模型却已经是可交付的：账本本身就有用
（"我这个月改了哪些仓库、多少轮返工"），而它同时是后续所有能力的地基。

**参考 Hermes 的 nudge 设计**：它用计数器（默认每 10 轮）触发一次后台复盘，
而不是每轮。这个量级是对的。

### 决策 3：团队共享走 git，不造同步机制

**选项**：
- (a) 自建中心服务（作者运营）
- (b) P2P 同步
- (c) 用户自带的 git 仓库
- (d) 用户自带的 HTTP 后端

**选 (c) 为主 + (d) 为辅，且 (a) 明确不做。**

理由：

1. **DSH 已经原生发现 `<仓库>/.agents/skills`（rank 200）和 `<仓库>/.dsh/skills`（rank 100）**
   （实测 `dsh-skill-filesystem` 的根列表）。也就是说——
   **把团队洞察写成 `SKILL.md` 提交上去，谁 pull 下来谁自动加载**。
   零服务器、零配置、天然版本化、天然可评审。**不需要发明任何同步机制。**
2. **不做 (a)**：一旦作者托管了服务，就成了数据控制者。这是法律红线，
   也是一个开源项目不该背的运营责任。
3. **不做 (b)**：冲突合并的复杂度远超收益。离线场景用本地队列解决就够了。

### 决策 4：数据用纯文本，不用宿主的存储抽象

DSH 提供了 `ctx.storage`（`storage-json` / `storage-sqlite` / `storage-domain`），
技术上能用。本项目**故意自己写文件**：

| 理由 | 说明 |
|---|---|
| 可移植 | 数据在 `~/.dsh-evolution/` 下是明确的，用户能备份、导出、搬走 |
| 离线 | 换 DSH 版本、换 composition、没挂 storage 插件时功能不能消失 |
| 可审计 | 纯文本 = 用户能亲眼确认"它到底存了我什么"，这是信任的基础 |

**索引是例外**：Phase 1 起引入 SQLite 也只**作为可重建的索引**，
真相源永远是纯文本。索引删掉能重建，用户手改 markdown 以用户为准。

### 决策 5：默认值全部取最保守的一侧

| 开关 | 默认 | 理由 |
|---|---|---|
| 记录账本 | ✅ 开 | 纯本地、零成本 |
| **自动复盘** | ❌ 关 | **花用户的钱**（调用户自己的模型） |
| **上传** | ❌ 关 | |
| **写入用户仓库** | ❌ 关 | 会在用户的 git 仓库里建文件，可能被误提交/触发 CI |
| 向量检索 | ❌ 关 | 会把正文发往用户配置的端点 |
| 连数据库 | ❌ 关 | |
| 跨工作区聚合 | ❌ 关 | 跨越了雇主/项目边界，最敏感。**手动晋升通道**已实现（`洞察` →「个人进化」）：插件只列出够格的候选与不够格的原因，由人点一下把某条经验提升为跨仓库提醒，随时可退回。自动聚合不做，也不建议做 |

**"默认关"不是保守，是让用户第一次打开面板时不需要先去关掉一堆东西。**
第一次体验必须是"它只在我自己电脑上"。

### 决策 6：提供"试跑"，让用户先看再决定

**这是 Phase 0 就必须有的，不是锦上添花。**

理由回到 §一 的那条判断：归纳质量差的项目，价值是**负的**。
错误结论会被注入到所有人的上下文里，而且长期生效。所以用户必须能在
**打开开关之前**就看到：会产出什么形状、会占多少上下文、大概花多少钱。

试跑的**核心不变式是"不回写"**，而且它靠**结构**保证、不靠调用方自觉：

- `lib/dry-run.js` **只 import 读取类原语**（`ledger.query`），不 import 任何写函数
- `lib/inject.js` 是纯函数、零 IO，渲染与预算计算都在里面
- **试跑与真实注入走同一条渲染路径**（同一个 `renderInjection`），
  否则"试跑看到的"和"真正注入的"会漂移，试跑就没有可信度

验证方式也是结构化的：冒烟测试对比试跑前后整个数据目录的**文件指纹**，
另有一项测试扫源码确认 `dry-run.js` 里不出现写函数名和 `fetch(`。

试跑页还会如实回答一个用户其实更关心的问题：
**"当前这个开关状态下，这次会话到底会不会真的跑？"**（`gate.wouldRun`）
—— 而不是让用户自己从一堆配置项里推断。

### 决策 7：数据库对接只做本机 SQLite，且是显式开关（2026-09-19）

`config.database.*` 作为配置契约存在了很久，本轮落地为实现（`lib/storage-sqlite.js`）：

| 判断 | 说明 |
|---|---|
| **默认仍是本地文件** | `database.enabled` 默认关。"连数据库 ❌ 关"（决策 5）不变 —— 变化的是"开"意味着什么，见下 |
| **"开"= 本机 SQLite** | `node:sqlite` 标准库、零依赖、单文件（`<dataDir>/index.sqlite`）。不是中心化服务器 —— 数据仍在用户自己手里，"备份/搬走/删掉"还是复制/移动/删除一个文件 |
| **开启后 SQLite 是真相源** | 决策 4 说"SQLite 只做可重建的索引"；本决策把边界往前推了一步：**用户显式选择**后，SQLite 成为真相源（NDJSON 不再读写）。之所以可以放开：数据仍在本机单文件里，且 `insight_ops` 表保留了完整的追加式操作日志 —— 可审计性没有丢，只是换了个载体 |
| **存量可迁移、可回退** | 首次启用把旧 NDJSON 一次性导入（幂等），**原文件保留不动**；删掉 index.sqlite 再重启 = 完整回退到文件形态 |
| **postgres 只有契约** | `docs/DB-CONTRACT.md` 是给 postgres 实现者的契约；没实现之前开着只会得到显式警告 + 文件回退，绝不静默 |

实现形态上刻意选了**最小方案**：洞察库只建 `insight_ops` 一张表（真相源），
"当前状态"靠每次 load 重放（与文件形态同一纪律）—— 量级是"人一生写下的经验"，
重放是毫秒级，不值得为此维护第二张物化表。契约方法清单与行为语义的权威在
`lib/storage-adapter.js`；测试的锚是"同一场景跑文件与 SQLite 两个后端，读出结果
必须完全一致"（`scripts/smoke.mjs` 等价性用例）。

### 决策 8：远程存储只做"契约 + 客户端"，服务端自建（2026-09-20）

`api.storageBackend`（默认关）把账本与洞察的读写整体指到 `api.baseUrl` 的服务：

| 判断 | 说明 |
|---|---|
| **插件仍不托管服务** | 决策 3 不变。仓库附带 `scripts/reference-server.mjs`（本地文件后端实现全部端点）作为**参考实现**，不是要部署的官方服务 |
| **默认关 + 三重条件** | `api.enabled + storageBackend + baseUrl` 缺一即回退本地文件并显式告警；401/403 后客户端**永久停止发送**（契约：鉴权失败不重试） |
| **定位变化已写明** | 开启等于把本机数据交给那台服务 —— 这是用户显式做出的隐私决定，面板与日志都会说明 |
| **零业务逻辑客户端** | 去重合并/复现计数/晋升语义全在服务端；客户端只做传输（超时/信封/鉴权）。三方等价性测试（本地直连 vs SQLite vs 远程）保证读出结果一致 |
| **离线容错** | 账本失败保缓冲重传（服务端按自然键去重）；错误进 `lastError` 面板可见，绝不阻塞宿主 |

## 三、从 Hermes Agent 学到什么、不学什么

实测了 Hermes Agent 本体源码（`%LOCALAPPDATA%\hermes\hermes-agent`）。它的"自动进化"是：

```
每 10 轮（nudge 计数器）
  → 在响应交付给用户之后，fork 一个受限子 agent
  → 重放对话快照，问自己"该不该更新技能/记忆"
  → 直接写 MEMORY.md / SKILL.md
空闲且距上次超过 interval_hours
  → curator 起一个 fork 整理技能库
```

### 抄的

| 抄什么 | 为什么 |
|---|---|
| **攒够 N 轮再复盘** | 逐轮成本 N 倍且看不到跨会话模式 |
| **在响应交付之后才跑** | 绝不和用户的任务抢模型注意力 |
| **review fork 工具白名单** | 复盘者只能改记忆/技能，不能碰代码 |
| **curator 三铁律** | 只碰自己创建的 / 只归档不删除 / pinned 绕过所有自动转换 |
| **注入分 stable / volatile 两层** | 技能索引进 stable（可缓存），记忆快照进 volatile（每轮重算）。否则每加一段就破一次前缀缓存 |
| **明确的"不要记什么"清单** | 见下 |
| **进化单位是 skill** | 见 §一 |

**Hermes 的"不要记什么"清单**（`background_review.py:271-290`）值得整段抄，
尤其是这条（这是全篇最值钱的一句）：

> 不要记录**对工具/功能的负面断言**（"browser tools do not work"、"X tool is broken"）——
> **These harden into refusals the agent cites against itself for months after the
> actual problem was fixed.**

一旦这类结论被沉淀并被注入，它就会变成 agent 长期拒绝干活的借口。
所以本项目在 `ledger.js` 里对工具失败判定**刻意保守**：
只有明确看到 `isError === true` / `error` / `ok === false` 才判失败，
**不确定时判成功**。误报失败会直接产出这类假结论。

### 不抄的

| 不抄什么 | 为什么 |
|---|---|
| **单一全局记忆文件** | 它一个 `MEMORY.md` 管所有项目。我们一个工作区几十个 git 仓库，必然互相污染 |
| **无评审自动写入** | 它承认会出事，用"只归档不删"兜。我们做的是要给别人用的通用插件，错误约束被发现前已经生效了 |
| **未提交状态只放内存** | 它的 generation 状态是模块级 dict，`kill -9` 就永久丢失，且只用 `logger.debug` 记一句。**水位必须落盘** |
| **依赖宿主 prompt cache 省钱** | 它 fork 复用父 agent 的 cache 所以便宜。我们不是主对话，拿不到这个 cache，所以必须靠"攒够 N 轮"+ 预算刹车控制成本 |

## 四、Phase 1 设计（已实现）

> 这一节原来写的是"下一步打算怎么做"。Phase 1 已经落地，所以下面改成
> **实际建成了什么**，并保留当初的判断与后来被证伪的部分（被证伪的会显式标出来）。

### 4.1 接入模型：`ctx.llm`，不需要用户再填 key

宿主提供 `ctx.llm`，任何插件都能调用**用户已经配好的模型**。
这是通用版可行的第一支柱：**DSH 用户本来就已经配好了模型**，否则他没法用 DSH。
让用户注册账号、填 API key、选模型，绝大多数人会死在这一步。

**实际实现（`lib/llm.js`）与当初设想有四处不同，都是有原因的：**

**① 不 import `@deepseek-ai/dsh-llm` 的任何东西，消息对象按契约手工构造。**

这个插件是被 `dsh plugin add` 静态安装的，它的 `node_modules` 里**没有**
`@deepseek-ai/*`（那些只在宿主那边）。所以 `createUserMessage()` 这类工具函数
根本 import 不到。做法是照契约手写一条消息：

```js
{
  id: 'dvev-<时间>-<随机>',
  role: 'user',
  content: [{ type: 'text', text: prompt }],
  source: { kind: 'plugin', plugin: 'dsh-evolution' },   // 宿主 forAdapter() 会读它，必需
}
```

`source.kind` 写 `'plugin'` 而不是 `'user'`：这条消息不是用户说的，是插件替自己发的请求，
宿主将来在轨迹里展示时，用户能据此区分"我说的话"和"插件替我发的请求"。

**② 拿服务必须走 `ctx.inject(['llm'], cb)`，根 ctx 上的 `ctx.llm` 会抛异常。**

cordis 对未声明依赖的服务访问是**抛异常**（`cannot get property "llm" without inject`），
不是返回 `undefined`。所以"顺手读一下 `ctx.llm`"在插件根 ctx 上永远失败。
`lib/index.js` 里两条路都走：`ctx.get('llm')`（服务已注册时直接拿到）+ 
`ctx.inject(['llm'], cb)`（服务就绪时回调），谁先到用谁 ——
只用 `ctx.get` 会在"恰好还没注册"时误报"宿主没有模型服务"，
而那个误报会让面板上的「现在复盘」按钮直接禁用。

**③ 一次流 === 一次尝试，不自己重试。**

宿主不做重试（那是 `dsh-llm-retry` 的事），所以这里也不做静默重试：失败就失败，
返回**稳定错误码**给面板。用户看到 `RATE_LIMIT` 和看到 `fetch failed` 的应对完全不同，
靠匹配文案分支是不行的。码表：`NO_SERVICE` / `NO_PROVIDER` / `TIMEOUT` / `ABORTED` /
`EMPTY_RESPONSE` / `BAD_JSON` / `NO_ADAPTER` / `MISSING_CREDENTIAL` / `AUTH` /
`RATE_LIMIT` / `CONTEXT_WINDOW_EXCEEDED` / `UNKNOWN`。
失败是从 `finish.reason.kind === 'error'` 里读出来的，但也留了兜底 catch ——
宿主版本差异不该让复盘崩掉，而应该变成一条"这次没成功"的记录。

**④ 模型怎么选：不猜名字。**

优先级是「配置里指定 → 内存里这个会话最近一次请求用的（`request/header` 事件缓存）
→ 宿主会话日志里的请求头（`sessionQuery.readSession` + `requestHeader()`，**跨重启也成立**）
→ 账本里最近一条带 model 的记录」，最后才是"用宿主注册的第一个 provider"。
**"猜一个模型名"是错的**：名字猜错会得到 `NO_ADAPTER`，而那条错误信息对用户毫无帮助。
所以宁可明确返回"需要你填"，也不编。

**⑤ "需要你填"不等于"给你两个空输入框"。** 早期版本把 `review.provider` / `review.model`
直接摆成文本框，结果是用户**不知道该填什么** —— 他不知道自己的 DSH 里有哪些 provider、
哪些 model，而唯一能告诉他这些信息的正是宿主自己。所以面板加了模型选择器：
`listModelCatalog()` 把 `listProviders()` × `listModels()` 摊开让他**选**。
选择器里那个「跟随当前会话」的选项**已删除**：留空现在表示**完全不复盘**
（`resolveModel` 的 `source` 只有 `config` / `none`）—— 花谁的钱必须是用户自己说的，
而不是让后台功能悄悄顺着会话里那个（往往最贵的）模型跑。这一项**只有一个下拉，面板不做手填** ——
能填的入口就会有人填错，而"哪些模型真的可用"只有宿主知道；已经写在配置里的旧值
仍会作为「当前配置里的值」显示出来并原样保留（适配器允许未列出的 id，但那是配置文件的事，
不是面板的入口）。

**花的是用户的钱，所以配套的这些一个都不能少（都实现了）：**

| 措施 | 落实在哪 |
|---|---|
| 默认 `review.enabled = false` | `config.js` 默认值 + `reviewGate` |
| 攒够 N 轮才跑 | `review.extractAfterTurns`（默认 10） |
| 会话静默才跑 | `review.idleDebounceMs`（默认 60s，每会话一个防抖定时器） |
| **每日 token 预算刹车** | `checkBudget()`：超了当天拒绝，并把原因写进返回值 |
| **同一会话不重复烧钱** | 水位 `state.review.watermarks[sid].records` + `minNewRecordsPerRun` |
| **一键暂停** | `review.pauseUntil`，`reviewGate` 立刻生效 |
| **失败码处理** | 见上，面板按 code 分支 |
| **模型不可用时不阻塞主会话** | `runReview` 把一切失败变成结构化报告；注入段求值出错只返回空串 |
| **并发保护** | `runtime.review.running`：连点按钮不会变成三份账单 |
| **失败退避** | 失败后 5 分钟内不再自动打模型 |
| **进度可见** | 面板复盘中每 1.5s 轮询运行状态，显示阶段（读账本/调模型/校验/入库）与已耗时 —— 没有进度的长时间等待会被当成"卡住了"，下一步就是狂点按钮 |

### 4.2 归纳产出的可信度门槛

| 规则 | 值 | 实现位置 |
|---|---|---|
| 每条洞察必须有**证据链**（sessionId + 轮次 + 原文引用） | 强制 | `insight-rules.js` `validateInsight`：两者都没有 → 直接拒收 |
| 晋升为项目级要求 `recurrence >= 3` | 强制 | `promotionVerdict` + `PROMOTION_DEFAULTS` |
| 自动晋升起点 | **仅 `session` → `repo`** | `promotionVerdict` 要求当前作用域必须是起点 |
| `team` 作用域 | **永不自动晋升** | 同上，显式判 `toScope === 'team'` → 不合格 |
| 被降级过的条目 | **永不自动晋升** | `promotionEligible === false` |
| 已归档的条目 | 不晋升 | 同上判 `archived` |
| 没有归属仓库的 `repo` 洞察 | 降为 `session` | 否则会污染所有仓库 |
| 同一次运行内模型自己重复的条目 | 合并，不新增 | `validateBatch` 内按归一化键去重 |

> 当初写的"无证据 / 低置信 → 落 `observations/`"**没有按原样实现**：
> 现在的做法是**直接拒收**并在复盘报告里列出拒收原因（面板可见）。
> 理由是"落一个不进索引的中间目录"对用户没有可操作性，
> 而拒收原因摆在面板上至少能让人判断"是模型答歪了还是规则太严"。
> `observations/` 目录目前是预留空目录。

### 4.3 归纳的 prompt 必须写死禁止清单（+ 代码层拦截）

三层防护，缺一不可：

1. **prompt 里的禁止清单**（`lib/prompt.js`）—— 请求模型别产出那几类东西
2. **代码层的入库前校验**（`lib/insight-rules.js`）—— 模型产出了也进不来
3. **人眼复核**（面板「洞察」页）—— 最后一道，也是唯一能发现"新类型错误"的

只做第 1 层是错的最常见形式：**prompt 是"请求"，不是约束**。

`prompt.js` 的写法上有几个刻意选择：先说要什么再说不要什么（只说禁止会让模型变得
极其保守）；给出**正例与反例清单**（模型对例子的理解远好于对抽象标准的理解）；
明确"没有就少说，返回空数组完全可以接受"；对禁止项**给出理由**而不是单纯禁止。

`insight-rules.js` 是一张**规则表 + 纯函数**（可逐条被测试打红），每类判定的去向：

| 命中 | 去向 |
|---|---|
| 对工具/功能的负面断言 | **拒收**（`negative-tool-assertion`） |
| 环境依赖的失败（`command not found` / 缺包 / 未配凭证 / 权限 / 网络） | **降级为 `fact`**、置信度压到 ≤0.35、取消晋升资格 |
| 会话内已自愈的瞬时错误 | 同上降级（教训是"重试/换法"，不是原始失败） |
| 疑似把密钥复述进结论 | **入库但标注 + 强制再脱敏** |
| 一次性任务叙述 | 标注 + 置信度压到 ≤0.3 |
| 标题为空 / 少于 4 字、没有证据 | **拒收** |

兜底的脱敏函数默认是"**脱敏**"而不是"原样通过"：如果哪天有人加了新调用点忘了传
脱敏函数，默认放行就等于把密钥写进库 —— 这个模块的全部意义就是"模型说了不算，代码说了算"。

### 4.4 检索：没有向量也要能用

三档，默认前两档（第三档只有配置项，没有实现）：

| 档 | 实现 | 默认 |
|---|---|---|
| ① 热条目直取（打分取 top-N） | `rankInsights`，**无依赖** | ✅ |
| ② 关键词全文检索 | `searchInsights`，**纯 JS BM25 变体，无依赖** | ✅ |
| ③ 向量召回（需用户自配 embedding 端点） | **未实现**，只留配置位 | ❌ |

> ⚠️ **原来的设计写的是"`node:sqlite` FTS5"，实际实现换成了纯 JS BM25**，
> 理由是 FTS5 的分词器对中文默认是"整串一个 token"（除非自己接分词器），
> 对中文用户等于不可用。现在中文用**二元组（bigram）**切分：
> 不完美，但零依赖、跨平台、行为可预期 —— 而"检索不到"比"检索得糙"更让人困惑。

打分是**确定性**的（同库 + 同配置必然同顺序，同分按 id 排），否则"试跑看到的"
和"真正注入的"会漂移，试跑就没有可信度了。权重全在 `SCORE_WEIGHTS` 一处：
作用域 6 / 类型 3 / 复现 log2 增长 / 置信 3 / 新近度 90 天半衰期最多扣 2 / pin +20。
归属不匹配的 `repo` 条目直接判 0 分 —— **注入了别的仓库的经验比不注入更糟**。

### 4.5 注入：stable / volatile 分层

| 段 | 层 | 预算（默认） |
|---|---|---|
| ① 强制约束（`constraint`） | stable | ≤3 条 / 300 字 |
| ② 项目洞察与避坑（`repo`） | stable | ≤3 条 / 400 字 |
| ③ 团队规范（`team`） | stable | ≤2 条 / 250 字 |
| ④ 个人提醒（`person` / `session`） | **volatile** | ≤1 条 / 200 字 |
| ③④ 的内容从哪来 | —— | **只能由人手动晋升**（`洞察` 页 →「个人进化」区块）。`promotionCandidates()` 只筛选、`migrate()` 只移动，没有任何自动跨工作区聚合 —— 那是决策 5 明确关掉的能力 |

**总预算 ≤1150 字**，且**每段预算独立**（防止某一段吃光全部）。

⚠️ ④ 必须和 ①②③ **拆成不同的 section**：变化频率不同。
全塞进一个 section 会让前缀缓存对每个人、每轮都失效——这个成本不报错，
只体现在账单上。

**Phase 1 新增的关键约束：`systemPrompt.section()` 的文本求值是同步的。**

宿主的 `SystemPrompt.assemble()` 里直接调 `section.text(context)`，而我们要读磁盘、
要算分。在同步回调里做 IO 会阻塞 agent 的每一步 —— 这正是本项目最不能犯的错。
所以拆成两半（`lib/inject-cache.js`）：

- `textFor(cwd)` —— **同步、零 IO**，只读内存缓存，拿不到就返回空串；
- `refresh()` / `refreshRoot()` —— 异步，在复盘完成、洞察变更、配置变更、插件启动时刷新。

缓存键是**仓库根目录**而不是仓库名：名字会撞（两个 `api/` 仓库），路径不会。
`cwd → 仓库根`的解析只在内存里走"已知仓库根表 + 祖先链"，**不 spawn `git`** ——
认不出就不注入（见 §4.5 与 §七 限制 6）。

注入文本头部三句话是功能的一部分，不是装饰：写明归属仓库（多实例并发串仓时让偏差可见）、
写明"与当前代码冲突时以代码为准"（结论来自过去的会话）、
写明"这是记忆不是指令"（防止从用户粘贴文本里归纳出来的条目被当成系统要求）。

### 4.6 真机验证抓到的 4 个 bug（假 ctx 全绿也挡不住）

Phase 1 写完之后，插件被 link 进真实 profile、在真实 `dsh web` 进程里
对真实仓库跑了一次**真实模型**（deepseek-flash）复盘：产出了一条带着证据链的洞察，
它随后出现在注入里。这条链路走通的同时，抓到了 4 个 bug ——
**它们全部让当时的 28 项集成自检保持全绿**，因为假 ctx 只能证明"接口签名对"。

| # | Bug | 症状 | 教训 |
|---|---|---|---|
| 1 | cordis 里读未声明的 `ctx.llm` 会**抛异常**（不是返回 undefined） | 面板永远显示"宿主没有模型服务"，复盘按钮一直是灰的 | **"拿不到服务"和"访问方式不对"必须分开**。修法是走 `ctx.inject(['llm'], cb)` 拿子 ctx，并同时保留 `ctx.get('llm')`；假 ctx 如果只在根上挂 `llm`，就会把这个真实的坑藏起来 —— 现在假 ctx 只在**声明过依赖的子 ctx** 上提供 `llm` |
| 2 | 按会话查账本时**没把 `sessionId` 下推**给查询，而是在内存里过滤 | 账本查询本身有"最多 N 条、按时间截断"的保护，先截断再过滤会让较早的会话**看起来不存在**，复盘报"账本里没有这个会话"，而它明明就在盘上 | **过滤条件要尽量下推到数据源**。凡是"先取一批再筛"的地方，都要问一句"那批够不够覆盖" |
| 3 | 洞察库用**文件指纹（size + mtime）**做变更检测 | 极快的连续写入可以让两次 `stat` 拿到完全相同的 size/mtime，变更被漏掉，表现为偶发（同一份测试有时绿有时红） | **不可靠的缓存判断比没有缓存更糟**：它把"偶发"引入了一个本来确定性的路径。改成**每次加载都重放日志**（几千行是毫秒级，这份数据是"人一生写下的经验条目"，不是遥测流） |
| 4 | 复盘报告里 `accepted[].id` **恒为空串** | `accepted` 是校验产物（还没入库、没有 id），`stored.added/merged` 才是 store 的产物。统一读 `item.id` 时前者永远是空的，面板拿它回查永远"找不到" | **同一个字段名在两条流水线上含义不同时，不要在展示层混用**。`brief()` 现在退回 `key`（去重键），至少是可定位的 |

**共同点：4 个都不报错，只是让功能悄悄不工作或偶发失灵。**
所以 Phase 1 之后多了一条纪律：**每个阶段结束时必须做一次真进程验证**，
并且验证要跑到"用户真的能看见结果"为止（这次是"洞察出现在注入文本里"），
而不是"接口返回 200"。

### 4.7 收尾阶段又抓到的 3 个（都在并发与两边对不上）

真机验证之后做收尾时，又有一批只在特定条件下才显形的问题被抓出来。
它们的共同点是**平时完全看不到，只在并发或"两边定义不一致"时出现**：

| # | 问题 | 症状 | 教训 |
|---|---|---|---|
| 1 | `writeFileAtomic` 只用 pid 命名临时文件 | 同一进程里两个异步写入（两次复盘同时收尾落 `state.json`）算出同一个临时路径，一个还在写、另一个已 rename 走 → 前者 `ENOENT`，或内容交错 | 临时文件名必须**每次调用都不同**（pid + 进程内自增序号 + 随机尾）。"并发才会撞"不是"不会撞" |
| 2 | `saveState` 是"读当前 → 合并 → 写回"，没有排队 | 两次交错互相覆盖：表现为"刚跑完的复盘在水位里查不到""暂停按钮没生效" | 任何**读-改-写**都要排队，哪怕它"看起来只会被调一次"。现在是一条 Promise 链，且链上挂"吞掉错误"的续接（否则一次失败会让后续所有写盘静默失效） |
| 3 | 面板调用的 RPC 方法与 host 的 `case` 会漂移 | 漏一个方法的症状是"点了按钮没反应"，语法检查与类型检查都发现不了 | 加了一项**包契约测试**直接扫两边：面板引用的每个 RPC 方法在 host 半必须有对应 `case`。同一组测试还守 `exports`/`files` 指向真实文件、版本号三处一致 |

> 第 1、2 条是靠**并发测试**逼出来的，不是靠读代码看出来的 ——
> 这类 bug 的验证方式是"让两个写操作真的同时发生"，而不是"再读一遍代码"。

### Phase 0 测试抓出的 6 个静默 bug（都有教育意义）

前 4 个在脱敏与配置层：

1. **ConfigStore 栈溢出** —— 数据目录由配置的 `dataDir` 决定，
   而"配置文件在哪"又由数据目录决定，形成 `current → loadSync → file → rootDir → current` 的环。
   解法：单开一条只读 `dataDir` 一个键、绝不回调 `current()` 的通道。
2. **脱敏正则捕获组编号错位** —— 把内层备选内联进组 1 后，`\2` 指到了备选组而非引号，
   导致 `key=value` 规则**永远匹配不上，且不报任何错**。
3. **键名被一起掩掉** —— `password=xxx` 整段变成 `●●●`，
   脱敏后读不出"这里被掩了什么"。
4. **负向前瞻被正则回退绕过** —— `(?![.(])` 时引擎会回退到更短的值让断言成立：
   `readFromVault` 匹配成 `readFromVaul`，只剩一个 `t()` 留在原地。
   必须用 `(?![.\w(])` 三个字符。

后 2 个出在**测试代码自己身上**，更值得警惕：

5. **测试数据用错类型名** —— 账本 kind 是 `user_message`（下划线），
   宿主事件名是 `user/message`（斜杠）。写测试数据时用了后者，
   `foldSessionSummary` 的 switch 全部不命中，**摘要静默变空**，
   靠 `turns === 2` 的断言才暴露。
   → 现在 `foldSessionSummary` 返回 `suspiciousInput`（一条都没认出来时显式标记），
   并加了一项「往返一致」测试：用 `foldEvent` 的真实产出喂给 `foldSessionSummary`，
   保证两边类型口径永远一致。
6. **async 检查写成了同步 `check()`** —— `integration.mjs` 里 3 个 async 检查
   传给了同步版 `check(fn)`，断言失败会变成 **unhandled rejection 而不计入失败数**，
   表现为"全绿但什么都没验"。→ 现在同步/异步分成 `check` / `atest` 两个函数。

**这 6 个全部不报错，只是悄悄做错事。** 所以两条纪律：
**改脱敏规则必须同时加测试；写完测试要用会失败的方式验证一次它真的会红。**

## 七、已知限制（诚实清单）

1. **DSH 没在跑的时候不会发生任何复盘。** 没有服务端定时任务，
   周期任务由插件进程内的定时器驱动。对个人版无所谓，对团队版意味着"得有人定期开着 DSH"。
2. **复盘会消耗用户自己的模型额度。** 所以默认关闭 + 预算刹车。
3. **归属判定用 `git rev-parse --show-toplevel`**：如果工作目录本身是个 git 仓库
   （比如 dotfiles 管理的家目录），该会话会被归到那个仓库名下。
   这是 `rev-parse` 的语义，不是 bug，但值得知道。
4. **工作区扫描上限 128 个一级子目录**，超限时返回 `truncated` 标记并在面板提示。
5. **`systemPrompt.section` 拿不到"本次组装属于哪个会话"**（宿主 scope 是 store 级的），
   所以注入侧只能维护"单一活跃仓库"状态。多实例并发不同仓库时会串仓——
   靠"在注入文本头部写明归属仓库 + 提示模型核对"让偏差可见。
   这是宿主层面的限制，待宿主支持后修。
6. **注入缓存只认真实见过的仓库。** `cwd → 仓库根`的解析走内存里的"已知仓库根表"
   （外加一次 `readdir` 看有没有 `.git`），**不 spawn `git`** —— 因为它是从同步的
   段求值路径上被调用的。代价：一个从没被插件见过的仓库，**第一次问答不会注入任何东西**，
   见过一次之后才一直有效。这是"宁可少注入，不要注错仓库"的取舍，不是 bug。
7. **去重合并是尽力而为。** 标题归一化 + 三道闸门（括号内容一致 / 数字一致 /
   骨架相似度 ≥0.75 或包含度 ≥0.6）的自动合并门槛刻意定得高，
   因为**合并错了会虚构复现次数**，而复现次数是自动晋升的唯一依据。
   合不上的靠面板上的**手动合并**（`insights/merge`）兜。
   标题里带空格的窄条目（`textSkeleton` 短于 10 字符）不参与自动兜底合并。
8. **成本估算是下界，不是预测值。** 面板上的预估按"输入 token + 输入的 15%"算
   （输出下限 200）。如果用户的默认模型开了高推理强度（`reasoningEffort`），
   模型会先生成大量思考 token，而**思考 token 也按输出计费**，
   实测里输出侧有相当比例是推理开销。所以预算刹车按**真实用量**记，不按估算记。
9. **配置项分"生效"与"预留"两类，且这个区分有测试守着。**
   文档审查一度发现 9 个面板可见但没有任何代码读它的开关（`retrieval.hotEntries` /
   `fullText` / `reSurfaceIgnored`、`review.onlyWhenIdle`，以及向量检索与两个 Phase 2
   参数）——**面板上的死开关比"没有这个功能"更糟**，用户会以为是自己配错了。
   处置分三种：
   · 能接线的接线（`hotEntries` / `fullText` / `reSurfaceIgnored` / `onlyWhenIdle`
     现在都真的生效，且 `fullText=false` 时检索**明确拒绝**而不是偷偷退回热条目）；
   · 功能没实现的参数从 `defaultConfig` 与 `SCHEMA_FIELDS` 里删掉
     （`review.repoRetroAfterTurns` / `personRetroIntervalHours` / `export.lastDir`）；
   · 属于"契约"的（`api.*` / `database.*`）保留并在字段上标 `reserved`，
     面板渲染成「预留 · 尚未实现」并写明原因。
   冒烟测试会扫描 `SCHEMA_FIELDS` 每一项，凡是没有 lib 代码读、又没标 `reserved` 的
   一律失败。
10. **"往外"的能力只有两项实现了**：写 skill 草稿（默认落插件数据目录，写仓库要显式确认）
    与本地导出。上传与向量化仍然只有配置项，没有任何实现；数据库例外 ——
    **本机 SQLite 已实现（决策 7，2026-09-19）**，它是写向"用户自己选择的本地文件"，
    不是"往外"，postgres 驱动仍只有契约（`docs/DB-CONTRACT.md`）。
